Historias, criterios de aceptación, tareas y prompts de IA para una iteración colaborativa de seis integrantes.

Propósito: convertir el modelo de datos de Control de Calidad en trabajo planificable y verificable, desde la definición de planes hasta el seguimiento de acciones CAPA y la prueba integrada.

Documento de referencia: specs/002-quality-control-module/data-model.md

Asignación sugerida basada en los seis integrantes nombrados en el modelo de datos. El grupo puede ajustar responsables y alcance con el profesor.

Cómo usar este documento

  1. Revisen las historias y criterios de aceptación en conjunto; confirmen reglas de negocio y dependencias con los otros módulos.
  2. Usen las tareas como base para el archivo tasks.md o el tablero de la iteración. Cada tarea debe tener responsable, estado y evidencia de revisión.
  3. Cada integrante puede enviar el prompt de su historia a la IA. La IA ayuda a producir una propuesta; el equipo valida y acuerda antes de integrar cambios.
  4. Integren cambios en una rama común y ejecuten las pruebas del flujo completo antes de presentar la versión de prueba.

Reglas compartidas para evitar supuestos

  • El modelo usa identificadores INT y depende de productos, empleados, recepciones, órdenes de producción y despachos. Acordar contratos y mapeos con los equipos responsables antes de conectar módulos.
  • reference_module + reference_id es una referencia polimórfica: debe validarse como pareja; no es una FK convencional.
  • El esquema no define cómo comparar automáticamente valores esperados y tolerancias (ambos son texto). No inventar una fórmula: acordar la regla; hasta entonces registrar el valor medido y el dictamen pass_fail según la decisión del usuario.
  • El esquema no define transiciones automáticas entre estados de inspección, no conformidad y CAPA. No cerrar registros automáticamente sin una regla aprobada.
  • Si un módulo externo no está listo, usar datos de prueba identificados como simulados y documentar el límite de integración.

US-01 · Prioridad alta

Administrar planes y criterios de inspección

Historia: Como responsable de calidad, quiero crear y mantener planes de inspección para un producto y etapa operativa, con sus criterios, valores esperados y tolerancias, para que las inspecciones sigan pautas definidas.

Valor: estandarizar qué se inspecciona antes de ejecutar controles de calidad.

Criterios de aceptación

  1. Dado un producto disponible, cuando el responsable crea un plan con nombre y etapa permitida (incoming, in_process o final), entonces se guarda vinculado al producto.
  2. Cuando agrega un criterio al plan con nombre y valor esperado, entonces queda asociado al plan; la tolerancia puede quedar vacía.
  3. Si falta un campo obligatorio o la etapa no es válida, el sistema impide guardar e informa qué corregir.
  4. El responsable puede consultar y editar planes y criterios existentes; los cambios se conservan al recargar.
  5. Un plan con inspecciones asociadas no se elimina silenciosamente: el sistema informa el impacto y aplica la política de borrado que el equipo acuerde.

Datos: quality_inspection_plans, quality_inspection_criteria, referencia a products.product_id.

Responsable sugerido: Eduardo Andrés Plaza Palacios

Tareas

  • Definir validaciones de plan/criterio y acordar política de edición/eliminación con relaciones existentes.
  • Diseñar la pantalla o formulario de planes y criterios siguiendo los patrones del proyecto.
  • Implementar persistencia y operaciones de crear, listar, editar y eliminar según la política acordada.
  • Agregar pruebas unitarias de campos obligatorios, etapa válida y asociación criterio-plan; documentar el contrato de producto.

US-02 · Prioridad alta

Registrar una inspección vinculada a su origen

Historia: Como inspector de calidad, quiero registrar una inspección basada en un plan, asociarla a mi usuario y al registro operativo correspondiente, para mantener trazabilidad de qué se revisó, cuándo y dónde se originó.

Valor: relacionar cada revisión con una recepción, una orden de producción o un despacho verificable.

Criterios de aceptación

  1. El inspector puede crear una inspección seleccionando un plan existente, un inspector válido y una fecha.
  2. El origen debe identificar tanto un tipo permitido como un ID: goods_receipt, production_order o shipment junto con reference_id.
  3. Si falta el plan, inspector, fecha o referencia válida, no se guarda y se presenta un mensaje de validación claro.
  4. La inspección guardada aparece en el listado con su plan, fecha, origen y dictamen permitido cuando este se registre.
  5. Cuando no estén disponibles los módulos origen, la prueba usa registros simulados identificados y no presenta la simulación como integración real.

Datos: quality_inspections, referencia a plan, employees.employee_id y origen polimórfico.

  • Validar el par reference_module/reference_id mediante integración acordada o adaptador de prueba.

US-03 · Prioridad alta

Registrar resultados por criterio y dictamen

Historia: Como inspector, quiero registrar el valor medido y el resultado de cada criterio de una inspección, y guardar el dictamen global, para dejar evidencia completa de la evaluación.

Valor: capturar los resultados en el nivel de detalle definido por el plan.

Criterios de aceptación

  1. Para cada criterio del plan de la inspección, el inspector puede registrar un valor medido y marcar si cumple o no (pass_fail).
  2. Un resultado sin inspección, criterio, valor medido o dictamen no se guarda; el sistema explica qué falta.
  3. El dictamen global permite únicamente passed, failed o conditional.
  4. Los resultados guardados pueden consultarse junto con la inspección y sus criterios, y permanecen tras recargar.
  5. El sistema no calcula automáticamente el cumplimiento desde texto libre de valor esperado/tolerancia mientras no exista una regla aprobada.

Datos: quality_inspection_results, quality_inspections.overall_result y criterios del plan.

Responsable sugerida: Carla Antonia Llanos Leal

Tareas

  • Definir con el equipo la captura del dictamen por criterio y global, sin asumir cálculo automático.
  • Implementar formulario/listado de mediciones asociado a la inspección y sus criterios.
  • Validar campos requeridos, estados permitidos y pertenencia del criterio al plan inspeccionado.
  • Agregar pruebas para medición incompleta, criterios no relacionados, dictámenes válidos y persistencia.

US-04 · Prioridad alta

Registrar y dar seguimiento a no conformidades

Historia: Como responsable de calidad, quiero registrar una no conformidad originada en una inspección fallida, indicando producto, descripción, severidad y estado, para controlar desviaciones detectadas.

Valor: dejar constancia trazable de defectos y su nivel de impacto.

Criterios de aceptación

  1. Una no conformidad requiere inspección, producto y descripción; no se guarda si falta alguno.
  2. La severidad se limita a minor, major o critical; el estado se limita a open, under_review o closed.
  3. La vista de detalle permite rastrear la no conformidad a su inspección y producto asociado.
  4. El responsable puede consultar y actualizar la severidad o estado; los cambios se conservan.
  5. Un cierre no modifica automáticamente el estado de CAPA, salvo que el equipo acuerde explícitamente esa regla.

Datos: non_conformances, relación con inspección y producto.

  • Implementar registro, listado, detalle y actualización de severidad/estado.
  • Conectar la inspección y producto con contratos disponibles o datos simulados debidamente identificados.
  • Agregar pruebas de campos obligatorios, enumeraciones, relaciones y actualización de estado.

US-05 · Prioridad alta

Asignar y seguir acciones correctivas o preventivas

Historia: Como responsable de calidad, quiero crear acciones CAPA para una no conformidad y asignar un responsable, una descripción, una fecha límite y un estado, para dar seguimiento a su resolución.

Valor: convertir la detección de una desviación en trabajo responsable y rastreable.

Criterios de aceptación

  1. Una acción requiere una no conformidad existente, empleado responsable, descripción y fecha límite.
  2. El estado solo admite pending, in_progress o completed.
  3. El responsable puede consultar las acciones de una no conformidad, cambiar responsable/fecha/estado y conservar los cambios.
  4. Una referencia inválida a una no conformidad o empleado impide guardar e informa el problema.
  5. La interfaz no cierra automáticamente la no conformidad al completar una acción, salvo que se acuerde y documente esa regla.

Datos: corrective_actions, referencias a no conformidad y employees.employee_id.

US-06 · Integración y calidad

Consultar la trazabilidad y probar el flujo integrado

Historia: Como integrante del equipo de calidad, quiero recorrer una inspección desde su registro de origen hasta sus resultados, no conformidades y acciones CAPA, para demostrar que el módulo integrado conserva las relaciones y permite seguir la resolución.

Valor: verificar el producto completo, detectar errores de integración y presentar evidencia de prueba.

Criterios de aceptación

  1. Desde una inspección se puede identificar el plan, inspector, fecha y origen; desde ella se consultan resultados y no conformidades.
  2. Desde una no conformidad se consultan las acciones CAPA con responsable, vencimiento y estado.
  3. Un escenario integrado de prueba crea/consulta el flujo inspección → resultados → no conformidad → acción CAPA y verifica que no haya relaciones huérfanas.
  4. Los contratos, mapeos de identificadores, datos simulados y limitaciones de módulos externos quedan documentados en el resultado de prueba.
  5. Se ejecutan las pruebas automatizadas pertinentes y una revisión manual del flujo; cualquier fallo se informa, no se presenta como éxito.

Datos: relaciones de todas las entidades de calidad y referencias externas descritas en el modelo.

Lista mínima para la prueba integrada

  • Producto y empleado de prueba disponibles o mocks claramente señalados.
  • Un plan con al menos dos criterios; una inspección con origen y referencias válidas.
  • Resultados guardados y dictamen global permitido.
  • Una no conformidad enlazada a la inspección y al producto.
  • Una acción CAPA enlazada, asignada a un empleado y con fecha/estado válidos.
  • Verificación de relaciones y persistencia tras recargar; errores intencionales de referencia probados.
  • Registro de comando de pruebas, resultado real, fallos conocidos y dependencias simuladas.
Importante: este documento organiza historias y trabajo; no implementa por sí mismo el módulo. La versión integrada de prueba se completa cuando los cambios de código y pruebas se ejecutan juntos.
